# Mario Kart World

Switch 2, `0400C3F00006E000`, 1.0.0 (`ResourceSizeTable.Product.100`). Bring-up in progress (wave 3): headless on the Mac a scripted route goes from a new save through the title, the menus, Grand Prix, the Mushroom Cup and its opening movie to the first race (Mario Bros. Circuit: HUD, lap counter, minimap and countdown on screen) without a crash ([Route on the Mac](#route-on-the-mac-wave-3)). Every 2D screen renders right; the 3D scenes are still mostly black or unlit, the movie does not reach the window, and with the compute passes running the game makes 10-20 fps ([Measurements](#measurements-on-the-mac-wave-3)).

## What the profile needs and why

- `switch2 on`: from `main.npdm` (`profile_guess.py` `switch2`). The host then answers as a Switch 2: 31.25 MHz counter, six cores, the Switch 2 kernel's `GetInfo` ids and svc 0x80.
- Memory: the Switch 2's 12 GB layout. `app_pool 0x265100000` (9809 MiB, the application pool); `nninitStartup` (`main+0xc387b4`) sets a heap of (total − used) rounded down to 2 MB less 0x60400000, 0x200c00000 here, which the 8.25 GiB heap region of `mem_reserve 0x348000000` holds. `sys_resource 0x4000000` from the NPDM. The alias region (`mem_alias 0x118000000`) has held everything the boot maps so far.
- `shader_groups`: where its NVN2 shaders live (`Shader/`, `Layout/`, `Effect/`, `Lib/`), for `shader_split.py`.
- `enc_thread on`: the main thread waits every frame on the fence of the frame just submitted, so the replay's Metal encoding is on the frame's critical path ([Frame pipeline](#frame-pipeline-wave-4)).
- `pso_manifest.tsv`: the prewarm list a first start prepares before its first frame, recorded from a whole Mushroom Cup in a window plus the headless route ([Frame pipeline](#frame-pipeline-wave-4)).

## The NVN2 device (wave 1 stop, resolved)

`nnMain`'s graphics setup (`main+0xcf3a14` on) makes these NVN calls first:

1. `nvnBootstrapLoader("nvnDeviceInitialize")` (`main+0xcf3a5c`) and `nvnBootstrapLoader("nvnDeviceGetProcAddress")` (`main+0xcf3a6c`).
2. Its C proc loader (`main+0xcf5560`) with a null device: every name it uses through `nvnDeviceGetProcAddress` (698 names; all in `names.txt` now).
3. The device builder's `SetDefaults` and `SetFlags(0)` (through main's pointers at `main+0x3304378` / `+0x3304380`) on a builder at `sp+0x10`; a 0x3000-byte device; `nvnDeviceInitialize(device, builder)`, which must return true.
4. The proc loader again with the device.
5. `nvnDeviceGetInteger(device, 0)` and `(device, 1)`: main requires API major 0xE7 (231) and minor 0x10 (16) or more (`main+0xcf3b20`).

With 55.15 `nnMain` left its graphics setup at `main+0xcf3d54` without creating its 0x260-byte graphics object (`main+0x33dcfb0`), and `sead::MethodTreeMgr` then read it (`main+0xe56e70`: `CRASH sig=11 addr=0x20`). Resolved: the host answers 231.16 with the NVN2 device-info table for Switch 2 games (b6d2fca8), and `nvnPrivate0` reads 0 at `nvnDeviceInitialize` ("NVN2: nvnPrivate0 is 0"), so main calls every fetched NVN function and inlines no header code.

### Look-ahead past the device check

`DM_NVN_API=231.16` (an existing diagnostic switch, no code change) makes the NVN1 implementations answer the version check, to see what comes after it. That runs NVN2 calls through NVN1 implementations of unverified ABI: what it shows about graphics is a list of names, not behaviour. The calls that followed, in order: `nvnDeviceGetInteger` items 0x2a, 0x5a, 0xf, 0x10, 0x11, 0x12, 0x55, 0x14, 0x19, 0x1a, 0x18; a 0x423000-byte memory pool (flags 0x22); a sampler pool of 4096 and a texture pool; `nvnQueueInitialize` (after `nvnQueueBuilderSetPrimaryQueue`, unimplemented); a 0x2d00000-byte pool and three 2560x1440 textures (format 0x25) for a three-texture window at interval 1; buffers; `nvnProgramBuilderSetDefaults` / `SetDevice` / `SetShaders` and `nvnProgramInitializeFromBuilder` (unimplemented); then from the frame threads `nvnCommandBufferSetRecordingMode`, `SetGeometryProcessingMode`, `SetStencilCullCriteria`, `ShadingRateImagePalette`, `BindShadingRateImage`, `PushGraphicsConstants`, `SetComputeOverlapMode` and `DrawMeshTasks` (all unimplemented). Every non-graphics call on that path was answered; the run ended in the host's shader hashing (`keys_hash` from `nvnQueueSubmitCommands`, reading a program through the NVN1 layout).

## Frame pipeline (wave 4)

PerfReplay, headless route `gp-race`, chain 8ae89a820186, runs in `$W/run/PerfReplay/` (`<run>.log`, per-frame `DM_NVN_TSV` rows in `<run>.tsv`, `sample` profiles `*_sample.txt`). Other agents shared the Mac (load 5-8, swap 4-5.6 of 5-6 GB used), so whole-frame numbers moved between runs by up to 2x; per-thread CPU costs are the stable comparison.

- Who does what (host backtraces at frames 1500 and 7000): the Presentation Thread (0x1004, priority 30) acquires the window texture (`main+0x262300`), submits the frame's commands, fences the game's frame sync (`main+0x262250`, `nvnQueueFenceSync`) and presents (`main+0x2623c4`). The window has 3 textures, all 3 active (`SetNumActiveTextures` is never called at run time; the dynamic 2 / 3 switch at `main+0x226d4e8` was not reached). The main thread starts each frame with two `nvnSyncWait`s: the acquire sync (`main+0x25ec58c`) and the frame sync of the frame the Presentation Thread just submitted (`main+0x25ec5a0`). So the game itself keeps at most one frame on the GPU: a frame is the submission's encoding plus the GPU's tail after it. Releasing the window texture at the fence of its replacing present (as on the device) only moved the wait from the first sync to the second (in-run A/B, run ab1).
- The game picks its present interval each frame: 1,500-1,900 interval changes per 330 s run headless (102 in the user's window session); with frames over ~17 ms it holds interval 2 for 40-95% of the race (`@itv` rows), which the host paces at 33 ms. Race frame-time medians are therefore bimodal and follow the interval more than the host's costs.
- Submit thread (race, frames 6000-7800, p50 per frame): CPU 6.7-7.1 ms (warm1, ab1), 5.4 ms with `enc_thread on` (enc1), 4.6 ms with that and the sparse range check (fin1); submit+present wall 6.9-7.4 → 4.4-5.0 ms. Before, `encode_args` was 43% of the submission, `tex_mtl` 20%, `nvn_sparse_since` 12% (74 of 616 samples, enc1), the residency-set commit in `sub_cut`'s `up_flush` 6%.
- GPU: 10.5-11 ms of execution per race frame (`@gpu_ms`), while the frame's GPU span (`@gpu_end_ms` − `@gpu_beg_ms`) was 17-21 ms p50 and up to 140 ms in long frames with no host cost (submit 7 ms, GPU 10 ms, no pipelines or uploads): the GPU idled inside one submission, with the system swapping (MemFix's shared sparse pages, c383bac2, cut the tile heaps behind it). p50 ≤ 16.7 ms needs the GPU tail after the submission (11-18 ms p50) to shrink; the host's remaining submit cost is 4.5 ms.
- Texture uploads are not what makes the long frames long: CPU deswizzle and upload encoding were 0.2 s over the 185 s race (max 4.6 ms a frame), GPU upload 66 ms; in the window session 1.25 s over 15 minutes for 26,254 first uploads, which fall in frames that are long for other reasons (course loads).
- First start (prewarm): without a list, a cold run waited 0.93 s by frame 3000 and 1.76 s by frame 6000 on the submit thread for pulling bases (145 bases compiled at about 65 ms each; menus 15-25 fps, run base_cold). With the recorded `pso_manifest.tsv` and the prepare step (`DM_PSO_PREPARE=1`, as with a window; run fin1, empty archive and `pso_user.tsv`): 6,521 lines prepared in 15.5 s before the first frame (3,138 bases compiled), then 124 ms of pipeline waits up to frame 3000 and none after. Mesh pipelines (11 a session) build in the background in 0.5-1.8 ms each.
- Window only (from the user's session log, not measurable headless): the display-link present is committed to the game's own Metal 4 queue (`present_now`: `[g_q4 waitForDrawable:]`, commit, `signalDrawable`), so until the compositor frees the drawable the queue holds every later command buffer of the game, which the main thread then waits for in its frame sync. ## Variable-rate shading (wave 4)

Measured with temporary record markers for the shading-rate calls, `DM_NVN_PASSDUMP`, `DM_NVN_GPUPROF` and raw dumps of the rate image (route `gp-race`, runs `$W/run/ShadingRate/sr1.log` and `sr3.log`, rate images `$W/ShadingRate/raw3/f<frame>_34222.png.raw`). The mechanism and the verdict are in [rendering.md](../../../docs/reference/rendering.md#variable-rate-shading-at-the-full-rate).

- Rate tables (`ShadingRateImagePalette` index, entries 0-15; 5 = 1×1, 6 = 1×2, 8 = 2×2, 9 = 2×4, 11 = 4×4):
  - table 0: 5 ×13, 8, 9, 11;
  - table 1: 5 ×4, 6 ×4, 8 ×6, 9, 11;
  - table 2: 8 ×14, 9, 11;
  - table 3: 5 ×16;
  - table 4: 8 ×16.

  MKW switches them on before the depth prepass and the lit pass of its 2560×1440 scene and off after. Before a 1280×720 pass it sets table 0 to `5 8 8 8 11 …` five times, without an image.
- The rate image is a 160×90 R8 texture (one texel per 16×16 tile of 2560×1440). In its 3D scenes (intro, title, race; not the menus) MKW draws it every frame in a one-draw 160×90 pass (0.8 ms). It binds the image there and unbinds it after the next two 2560×1440 passes, the lit scene passes.
- Texel histograms, with the share of fragment work they would save for table 0 and table 1 primitives:

  | Frame | Index 0 | Index 1-7 | Index 8-13 | Index 15 | Saved, table 0 | Saved, table 1 |
  |---|---|---|---|---|---|---|
  | 1500 (title) | 31% | 3% | 62% | 5% | 4% | 52% |
  | 2100 (title) | 87% | 1% | 8% | 5% | 4% | 11% |
  | 6300-7100 (race) | 47-52% | 2% | 43-48% | 1-3% | 1-3% | 36-40% |

  Index 15 covers rectangles under the HUD (item box, bottom left). Index 12 covers a wedge of near road at the bottom of the screen.
- Which table a draw uses (race frames 6400-6403, draws while a table is on): table 0 47% with the image bound, table 1 34%, table 2 15%, table 3 7%, table 4 under 1%. 1,758 vertex programs take the table index from `c[16][0x30]` per draw ([shaders-sm86.md](../../../docs/reference/shaders-sm86.md)). Without the image only table 2 and 4 draws would be coarse (entry 0 = 2×2): about 100 of the prepass's 978 draws.
- GPU time of the passes concerned, in frames without a pass dump: the lit pair takes 1.6 ms in the title (frame 2000) and 2.0-2.1 ms in the race (frames 6000, 6400, 7000), out of 7.7-8.4 ms of render-pass time; the prepass pair takes 0.4 ms. With a pass dump the same pair takes 6-7 ms, because the GPU idles between submissions. Upper bound of the saving: about 0.5 ms weighted by draw count, at most 1.9 ms if every fragment of those passes went to 2×2. The race is CPU-bound, so the frame would not get shorter. Not prototyped.
- Not measured headless: the share in a windowed session with the Metal HUD. The internal resolution is the same (2560×1440), so the bound holds. To check it in a window: `DM_NVN_GPUPROF=every:600` with the play script, then `dm/tools/gpuprof.py` on the log; the two 2560×1440 passes after the 160×90 pass are the ones concerned.

## Render resolution and NDSR (wave 4)

Headless, chain d1a62107da8c, the route above, `DM_NVN_PASSDUMP=every:1000` / `DM_NVN_GPUPROF=every:1000` with `DM_NVN_DISPATCH_OWN=1` (`$W/run/MetalFX/m1.log` console, `m2.log` handheld, `m3.log` / `m4.log` console with `DM_GRAPHICS_SCALE=2`):

- The 3D scenes render at the window's size, without a dynamic resolution: console mode 2560x1440 in the intro, title, menus, movie and race (scene colour RG11B10Float with Depth32Float_Stencil8 at 2560x1440, every viewport the whole target, frames 500 to 7500); handheld (`DM_OPMODE=0`) 1920x1080. The only scale the game applies comes from the system's graphics scale ([The Switch 2's graphics scale](../../../docs/reference/services.md#the-switch-2s-graphics-scale-oe)): `main+0x52321c` divides two sizes from the display object (`[main+0x32f1db8]`, virtual calls +0x118 / +0x120) and stores the quotient as the scale of all four screens (+0x43b8 / +0x43bc of each 0x4468-byte screen entry); `main+0x3cf40` multiplies the viewport by it, floored to a multiple of 4 between 8 and 16384. With `DM_GRAPHICS_SCALE=2` every scene, the race included, renders at 1706x960, and the final composite draws that texture over the 2560x1440 window with a linear sampler, the HUD on top (`m3.log` F2500 pass 288789).
- NDSR (`agl_ndsr.pck`, the "Ndsr upscale" entry (in Japanese) among agl's render passes, NintendoWare_Ndsr 1.1.0) is SMAA plus a single-image upscaling network. Its pass (`main+0x227ac1c` → `+0x227ad04`) reads its scale at +0x14 of its settings (`[pass+0x270]`): at 1.0 it runs SMAA alone into the given target (`+0x227af60`: `ndsr::smaa_edge`, `smaa_blendweights`, `smaa_output`, vertex / pixel 04a209f2e78754bd / 6f97a82553fc9820, 8e51162d7b83d387 / d6c0f83282009305, 44a7c58cc83a175c / 3b45dca2b9307e8c, the {1/W, 1/H, W, H} bank-24 programs); otherwise it makes `ndsr::two_step_upscale_input` at the scaled size, runs SMAA into it and then the network (`+0x227b15c`) into the target. The network's 30 compute programs (2fca37fc24373f0c … f765ab94d01c6241, local size 128, 15.9 KB shared memory, 2.7-5.6 MB of MSL each) each read one colour texture by texel and write one image: no depth, motion vectors, jitter, exposure or history. `main+0x3cfb0` uses the NDSR scale only when the pass's settings byte (from its bool parameter at +0x208) and the screen's bit in its mask (+0x228) are set.
- On the Mac the network never runs: none of its 30 programs is dispatched or even gets a pipeline in m1-m4 (console, handheld, graphics scale 2 through the race) nor in the user's whole Mushroom Cup at 150cc (`$W/run/play/pso_user.tsv`, 52,800 frames: 138 compute pipelines, none of NDSR's). So there is no NDSR dispatch to replace with MetalFX's temporal scaler, and the stretch the game does at a lower scale is one draw of its final composite, HUD included. A temporal scaler would also lack its inputs there: the frame has no motion-vector target (its 2560x1440 targets are RG11B10Float, Depth32Float_Stencil8, RGBA8, RGBA8 sRGB and RG8) and SMAA is its only anti-aliasing (no camera jitter to accumulate).
- NDSR's cost is its SMAA: in console mode 0.41-0.46 ms of GPU per frame at 2560x1440 (edge 116-144 µs, blend weights 140-230, output 132-255; frames 1000-8000, 5-7% of the frame's 8.3-9.5 ms of encoder time), 0.22-0.29 ms at 1706x960. Handheld runs no SMAA (none of the three programs in m2).
- The render scale buys little GPU time: the race's encoder sum is 7.5-8.5 ms at 1706x960 (m4, frames 6000-7500) against 8.3-9.5 ms at 2560x1440 (m1); the `[nvn] timing` GPU p50 10.5-11.4 ms against 11.2-11.9 ms. Most of the frame's GPU time does not depend on its size (sky-cube faces, 64x64 / 32x32 six-colour passes, compute, shadow maps), and the frame is CPU-bound anyway ([Measurements](#measurements-on-the-mac-wave-3)).
- The present's MetalFX spatial scaler (`DM_PRESENT_UPSCALE=metalfx`, [The present upscales through MetalFX](../../../docs/reference/rendering.md#the-present-upscales-through-metalfx)) on the picture a fullscreen 16-inch MacBook Pro shows (`DM_NVN_SHOT_OUT=3456x1944`, run m5 on chain 8ae89a820186, `$W/run/MetalFX/m5_<frame>.png` beside `m5_<frame>.bilinear.png` of the same frame; zoomed pairs `m5_6500_crop_bilinear_vs_metalfx.png` road, `m5_2490_crop_bilinear_vs_metalfx.png` title logo and canyon, bilinear left): MetalFX keeps the road's and the rock's texture and the logo's edges that the bilinear pass blurs, with no ringing visible; the mean absolute gradient is 1.6-1.8 times the bilinear one at every frame (title 2490 11.2 / 6.2, character 2990 4.1 / 2.6, kart 3190 5.3 / 3.4, movie 4800 4.9 / 2.9, race 6500 6.8 / 3.9). The HUD, drawn at 2560x1440 into the same window texture, is scaled with the scene. Cost: a steady scaler takes 0.56 ms of GPU per frame for 2560x1440 to 3456x1944 and 0.67 ms to the 3600x2260 window the user played in (p50 of 200 encodes, M5 Pro, `$W/run/MetalFX/fxbench.m`, measured with another MKW run on the GPU; the temporal scaler 0.84 / 0.94 ms); each shot's freshly made scaler took 1.3-8.1 ms on its first encode against 0.11-0.15 ms for the bilinear pass. Against the 13-17 ms of GPU of the user's fullscreen session (CPU-bound at about 27 fps) that is affordable; it stays a player choice (off by default, no profile key).

## Movies

All 49 RomFS movies (`Movie/*.webm`, the cup openings 2560x1440 at 60 fps, e.g. `KinokoOp.webm` 1,423 frames) are VP9 WebM without an audio track. The player (`main+0x6d7000`..`+0x711600`, decoder wrapper `main+0x19e5000`..`+0x19ee000`) feeds `nn::movie::MediaExtractor` itself (`AppendMediaSourceData`) and submits its samples to the `nn::codec` VP9 decoder:

- decoder created as codec 1 (VP9), output format 3, codec mode 1 (`main+0x7110c0`); `MakeDecodeImagePreference(w, h, 3, 1)` → layout code 1 (NV12); two to eight output buffers, each a one-image pool (`main+0x19e78a4`) registered at once (`main+0x19e60a0`);
- frames are waited for with `nn::syncpt::sdk` events: `TryWait`, `Cancel` if unsignalled, `Request` on the acquired buffer's handle, then a multi-wait over all buffers (`main+0x19e7760`, `+0x19e724c`);
- the buffers are type 1 (CPU, `main+0x711124`): each frame is copied out with `ReadDecoderOutputImageNv12` into the player's own w×h×3/2 buffer (`main+0x19e7950`) and uploaded through NVN; the native image handle path (type 3) is never used; images are released with an all-zero sync handle (`main+0x19e6e00`).

The host serves all of it: [The Switch 2's `nn::codec` video decoders and image pools](../../../docs/reference/movies.md#the-switch-2s-nncodec-video-decoders-and-image-pools), [Sync point events on host counters](../../../docs/reference/movies.md#sync-point-events-on-host-counters-nnsyncptsdk); `MediaExtractor` and the AAC decoder run as the game's own code. Checked headless with `dm/host/tests` `build/t_codec_video /Users/emanuel/Games/Switch/base/romfs/Movie/KinokoOp.webm 120 out.png`: the Mushroom Cup opening goes through the same SDK calls and frame 120 (2.000 s) comes out right (121 frames in 0.63 s).

## Shaders

`shader_split.py` finds 11,567 distinct NVN2 programs (3,550 vertex, 7,264 pixel, 728 compute, 7 task, 18 mesh) in 3.5 min:

- `Shader/*.bfsha` (BNSH), and the Drive sarc's two BAHS 11 `sharcb`, which hold every compute, task and mesh program of the drive passes;
- 79 Layout `blarc` BNSH;
- the Effect `esetb`'s two BNSH (3,136 programs);
- `Lib/`: agl, gsys, Terrain and Visualizer BAHS; `agl_ndsr.pck` (30 HMMA compute stages and 3 programs); sead's 6 font and primitive stages, which embed SPIR-V;
- main's two BNSH (40 programs).

There are no loose code areas: every program header in the RomFS and in main lies inside those containers. Keys are `sha256(control[0:0xd8] + code)[:16]`. `nvn2_dump.py` writes the programs to `$W/shader/sm86/` and a census to `$W/shader/sm86_census.tsv` (179 opcodes, 5.55 M instructions) for the SM86 work. The containers, control sections and keys are in [Switch 2 (NVN2) shader binaries](../../../docs/reference/shaders.md#switch-2-nvn2-shader-binaries).

Full translation (chain d28a1605604e, translator 2057b672; [Switch 2 translation](../../../docs/reference/shaders.md#switch-2-translation)): 11,540 of the 11,567 programs have Metal libraries in `$W/shader/cache/b-d28a1605604e` (vertex 3,549 / 3,550, fragment 7,264 / 7,264, compute 727 / 728); the 7 task and 18 mesh programs are not translated, and 2 are dropped for a global memory access through a pointer (compute 791fb7522aa03e61 loads, vertex 0459a55e79335cf6 stores; stages from `shader_map.tsv`). `c1_full.tsv` (13 shaders not proven bounded) and `cb_extent.tsv` are in the profile folder, inputs stamp 1dd894ea18d6. A full build takes 30 min with an empty Metal cache, 3 min after a translator rebuild. The 5 bank-24 fullscreen programs bind NVN2 push block 0.

The two programs with a global memory access through a pointer (current, chain 8ae89a820186, wave 4): 0459a55e79335cf6 is gsys's `clear_geometry_culling` vertex program (`common.sharcb` binary 161, with its fragment program; looked up by name at `main+0x9b0520`, gsys::GeometryCullingMgr): vertex i stores {0, 1, 0, 0, 0} through the i-th 64-bit pointer of its storage buffer, resetting an indexed indirect draw's arguments. 791fb7522aa03e61 is agl's `invalid_pixel_detector` compute program (`agl_common.sharcb` binary 1549, a name in agl's program table at `main+0x32663e0` beside `invalid_pixel_visualizer`): it counts NaN / infinite / out-of-range texels per kind and, with its storage buffer's word 0 set, adds the word at its pointer (words 14-15) + 0xf000a000 / 0xf000b000 / 0xf000c000 by kind to word 20. Neither is bound in the user's 52,800-frame Mushroom Cup session (`$W/run/play/play-20261101-110559.log`) nor in route run rt2: no "failed to load" line for either key, which the host prints at a program's first bind ([INFERENCE] the game's renderer does not use gsys's geometry culling, and the detector is a debug tool). They now translate through the global pointer table ([Global memory through a pointer](../../../docs/reference/shaders-sm86.md#global-memory-through-a-pointer)): all 11,567 programs have libraries in `$W/shader/cache/b-8ae89a820186` (3.5 min, 2 Metal compiles: the MSL of the other 11,565 is byte-identical to b-d1a62107da8c, their reflection differs only in `chain`). `t_gptr $W/shader/cache/b-8ae89a820186` runs both on the GPU: 5 records reset through pointers into three pools (one an alias), a pointer into no pool counted as 5 misses and logged; the detector read 2000 through its pointer for its one NaN texel (kind 1), and 0 with one miss through a pointer into no pool.

- The movie: resolved (2040efe2, [Movies](#movies)).
- NDSR's upscaling network does not run on the Mac in any mode measured ([Render resolution and NDSR](#render-resolution-and-ndsr-wave-4)): its settings keep the pass at scale 1.0, SMAA alone. If a mode does turn it on, its 30 HMMA programs run emulated with shuffles; their inputs (one colour texture in, one image out) are those of MetalFX's spatial scaler, not the temporal one's.
- Output streams and the socket calls behind Pia are served but not met on the route (the sound goes through the audio renderer: `audren: rendered 48000 frames, 44142 of them not silent`). Pia's network start (`main+0x22477b4`) stops at `nifm::IsNetworkAvailable` (false), before `nn::socket::internal::Initialize`; the SDK 19 socket overloads it would call next (`Socket(Family, Type, Protocol)`, `Bind(SockAddr)`, `SetSockOpt(Level, Option)`, `Close`, `EventFd*`, `GetPeerName(sockaddr)`, `GetAddrInfo` with resolver options, `Resolver{Get,Set}Option`, `IsInitialized`, `SetAllocator`) and `nn::ssl::Context::Create` (which returns 0xca7b without a service session) are not hooked; Online Play stays unavailable.
- AV1 movies: the host has no AV1 decoder (`InitializeAv1Decoder` fails with a red line); MKW has none.
- The Switch 2's display: `oe::GetDefaultDisplayResolution` answers the Switch's 1920x1080 / 1280x720; MKW does not import it.
- The open world's flat ground (the user's cup run: desert, canyon road, night forest): resolved by 65d58bf0 (GPU-written sparse textures). Free Roam before it showed flat beige, grey and reflecting white ground (`$W/run/RenderFix/off_5000.png`, `fr3_5500.png`); nx2 4acbc57f without texture upload keys shows grass (`nboff_4600.png`, `nboff_5000.png`). The terrain's colour draws (DriveRefreshUber Procedural, fragment 8eba28f059134a74 in pass 799827 of Free Roam frame 5500, depth prepass fragment 134fcb897eb723ca) sample per-tile 260x260 textures (`MINIMAL_LAYOUT`, a `CPU_CACHED | GPU_CACHED` pool, flags 0x24: R16 height, RG8 material with 9 levels, RGBA8, RG11B10F, BC1 / BC3 sRGB, and 516x516 BC1 sRGB), not the 8192x8192x68 arrays, which the model shaders (GridifyGeo) bind. Those tiles hold CPU-written data at first use (`DM_NVN_TEXINFO=260x260`: 135k of a height tile's 152k bytes non-zero), yet without `tex_flush_upload` / `tex_dirty_upload` only the block-compressed ones have it on the host (`DM_NVN_TEXRAW=info`: R16, RG8, RGBA8 and RG11B10F all zero). On the base before 65d58bf0 the two keys also gave a textured ground (`terrain_before_after.png`, the run's save spawns elsewhere each time); with 65d58bf0 the ground is textured without them, so what the zero tiles still cost is not known (the two keys back in `game.tsv` are the test).
- The item slots' mottled background: the frame is a layout user shader (`IconItemSymbol_01` blarc, `bgsh/ItemSlot_00.glsl` in `__ArchiveShader.bnsh`): texture 0 gives the dark disc's alpha and a rainbow gradation weight, texture 1 sampled three times at scrolled, scaled UVs (`fract`) gives `min` of its channels times a constant-colour gradation, added on top: shards that drift, by design. Not compared with the console.
